# GRDR Archive Transaction Contract

## Step isolation

The Plan step owns intent and locks. The Execute step owns evidence-backed staging and execution ledgers. The Archive step owns canonical promotion. No step may impersonate another:

- Plan must not stage or promote content records.
- Execute must not write `registry/*.jsonl`.
- Archive must not invent evidence, repair ledgers, or alter scope.

The only accepted Archive input is a sealed `archive_package.json` generated by `prepare-database-deep-map-archive` from an execution-ready project.

## Fingerprint chain

The package binds:

1. the audited diagnostic plan;
2. the declared scope;
3. the ordered work-unit manifest;
4. the current unit and route-check ledgers;
5. the complete staging manifest;
6. the package payload itself.

Archive must recompute each fingerprint. Any difference is stale state, not a harmless formatting change.

## Optimistic conflict control

Each staged record records one action and two content fingerprints:

- `create`: no canonical base existed at staging time;
- `update`: a canonical base existed and the staged content differs;
- `unchanged`: staged and canonical content were identical.

Before promotion, create IDs must still be absent. Update and unchanged IDs must still have the captured base fingerprint. An unchanged record must still equal canonical content. A violation blocks archival and returns the project to a new execution pass.

## Transaction and rollback

Promotion is successful only if the prospective merged registry passes strict Schema and integrity validation, the human catalog rebuild succeeds, the catalog check succeeds, the receipt validates, and the final project audit reports `completion_ready: true`.

If a post-write gate fails, restore every affected canonical collection, rebuild the catalog from restored canonical state, restore the project and manifest, and remove or restore the receipt. Partial canonical promotion is forbidden.

## Receipt semantics

`archive_receipt.json` is the durable transaction proof. It binds the package fingerprint, registry version, action counts, collection counts, validation output, archive time, and receipt fingerprint. A project is complete only while the receipt remains valid against the current sealed ledgers and manifest.

An archive call with an already valid receipt is idempotent. It must not rewrite canonical records or issue a second transaction.
